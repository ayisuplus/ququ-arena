## 6. 旧代码的清理标准

为旧模块建立“入口→引用→运行分支→替代模块→回归检查”的简表。源码整理的目标是减少重复职责和失效入口，而非按文件年份删减。

1. 先找编译引用、反射／字符串／Resources 动态入口、编辑器重建入口和测试用途。
2. 与当前启动版、备份版和制作源分别对应；历史源码进入带版本索引的归档，不混进活跃编译程序集。
3. 若某段旧实现仍承载当前可用功能，先迁移调用者、验证等价行为，再移除；不顺便美化相邻代码。
4. `.meta`、依赖资源和许可成套处理。一次只移一个明确功能簇，保留 Git 可回退提交。
5. 本轮没有完成全量 GUID／动态引用图，因此**没有任何源代码或游戏资产被认定为可以直接删除**。

## 7. 下轮执行顺序与回退

1. 冻结 HEAD、dirty／untracked 路径、大小、SHA-256、Junction 目标及当前启动入口；确认没有进程依赖拟移动目录。
2. 建立版本归档 manifest：原位置、目标位置、版本、哈希、必要依赖、恢复命令／步骤、恢复验证记录。目标必须是明确绝对路径，不能跟随 Junction 扫删。
3. 先复制、校验，再抽样恢复。归档当前版回退能力通过前，不移走旧版。
4. 处理启动器和后端链接，验证默认启动、回退启动、比赛／配置／外观加载。采用新运行包和旧运行包分离的目录，不覆盖当前版。
5. 清理已验证可重建缓存；运行相应重装／导入／检查，记录实际腾出空间和重建成本。
6. 再按完整依赖图分批整理代码与资产。未能证明可移除的条目留“待核实”，不强删以完成数量目标。
7. 只提交本轮可归属的变化，原有用户未跟踪证据保持原状。提交分别覆盖归档索引／启动入口／资产迁移，避免一笔不可审查的大提交。

若使用 Codex 管理的 worktree，先用 worktree 工具识别与归档，不用 shell 递归删除。独立仓库、运行数据和工作区外目录不随父目录打包或清理。
