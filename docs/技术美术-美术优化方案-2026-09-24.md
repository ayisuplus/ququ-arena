## 0. 一句话结论

**画面"干"不是美术能力问题，是三个工程默认值造成的**：所有程序化道具共用同一组 `_Smoothness/.65 + _Metallic/.35`、贴图全部 Uncompressed 且无平台分级、以及全项目零粒子。

前两个让材质读起来像灰模，第三个让打击完全没有接触反馈。三件事都能在不改任何建模的前提下改善，且**第一件和第二件是纯设置工程，不碰内容**。

### 1.1 管线设置（`Assets/Settings/PC_RPAsset.asset`、`PC_Renderer.asset`）

| 项 | 现值 | 判断 |
|---|---|---|
| 默认管线 | `GraphicsSettings` guid `4b83569d…` = **PC_RPAsset** | ✅ 正确，高级特性生效 |
| 渲染模式 | `m_RenderingMode: 2` = **Forward+** | ✅ 好，可支撑多光源 |
| 附加光模式 | `m_AdditionalLightsRenderingMode: 1` | ✅ 已核对 URP 源码 `LightRenderingMode { Disabled=0, PerPixel=1, PerVertex=2 }` → 是 **PerPixel**，不是隐患 |
| MSAA | `m_MSAA: 4` | ⚠️ **被 QA 锁死**：`ArenaVisualCheck.cs:57` 断言 `msaa>=4`。要改抗锯齿方案必须先改这条断言 |
| Opaque Texture | `m_RequireOpaqueTexture: 1` | ❌ **纯浪费**：全项目 shader 无一处采样 `_CameraOpaqueTexture`（已 grep 确认），却每帧多一次全屏 copy + 一张全屏 RT |
| SSAO | 开启，`Downsample: 0`、`Intensity 1.15`、`Radius 0.24` | ⚠️ 全分辨率 SSAO，建议 `Downsample: 1` |
| GPU Resident Drawer | `m_GPUResidentDrawerMode: 0` | ❌ Unity 6 的 draw call 大户优化**没开**，draw 138-628 有下降空间 |
| 阴影 | 45m / 4 级 cascade / 4096 主阴影图 / soft quality 3 | ⚠️ 偏奢侈；45m 对室内场馆过大，建议 24-30m 并把 cascade 收到 3 |

### 1.2 贴图与显存（这是最大的一块）

`Assets` 下 **93 张贴图、源文件 209 MB**。导入设置来自 `Assets/Editor/ArenaVisualBuild.cs:26-33`：

```csharp
importer.textureCompression = TextureImporterCompression.Uncompressed;
importer.anisoLevel = 16;
importer.mipMapBias = -.25f;
importer.maxTextureSize = 4096;   // 且没有任何平台 override → 移动端同样 4096 未压缩
```

三个问题：

1. **未压缩**：2K RGBA 未压缩带 mip ≈ 22 MB/张，这是专用显存 1.3 GB 的直接来源。
2. **格式不看用途**：`SourceNormal.png`（7-8 MB/张）是法线却存 RGBA32——应该用 **BC5**（8bpp，且专为法线设计，不会像 BC7 那样让 XY 分量压缩比不一致导致法线失真）。`MetallicSmoothness.png` 是单/双通道遮罩却存 RGBA32——应该用 **BC4**（4bpp）。
3. **`mipMapBias = -0.25`**：把采样推向更高级别 mip，换来轻微锐利感，代价是 aliasing + texture cache miss 上升。
4. **全局 `ForceEnable` 各向异性**：`ArenaStage.cs:100` 与 `ArenaVisualBuild.cs:17` 都设了 ForceEnable，会让**所有**被采样的贴图（含 UI、遮罩）都走各向异性过滤。

理论收益（不实测，只给算术）：

| 类别 | 现在 | 改后 | 倍率 |
|---|---|---|---|
| BaseColor / Portrait | RGBA32 32bpp | BC7 8bpp | **4×** |
| Normal | RGBA32 32bpp | BC5 8bpp | **4×** |
| Metallic/Smoothness/AO 遮罩 | RGBA32 32bpp | BC4 4bpp | **8×** |
| 移动端 | 4096 未压缩 | ASTC 6×6 @1024 | 数量级 |

### 1.3 光照与后处理

- 光源：`ArenaStage.cs:85-90` 1 盏主方向光（软阴影）+ 3 盏 FillLight 点光；**点光全部没设 `shadows`**，默认 `None`——这是"暗部平、物体发漂浮"的直接原因，不是管线限制。
- 展馆 6 盏点光同理无阴影。
- 程序化道具：`ArenaLightShow.cs:74` 对每个 Shape 显式 `shadowCastingMode=Off; receiveShadows=false`——几百个物件既不投也不收阴影，空间深度全靠 `_GalleryFill` 假补光撑。
- **所有程序化道具共用一组材质参数**：`ArenaStage.Mat()`（`ArenaStage.cs:41-47`）硬编码 `_Smoothness=.65`、`_Metallic=.35`，**不随材质名变化**。所以合金、陶瓷、石墨、标记带四种材质在画面上读起来是同一种"塑料灰"——这就是"灰模盒子"感的根因。
- 后处理：`ArenaStage.cs:94-99` 只有 Bloom(0.14/threshold 1.65) + ACES + contrast 7。无 Vignette、无景深、无动态模糊 → 缺少画面重心。

### 1.4 特效

**全项目零粒子系统**（grep `ParticleSystem` 确认）。掌击 0.48s 接触帧（`ArenaFighter.cs:206-207`）只有一个回调，没有任何视觉放大——打击感全靠动画曲线撑。

### 1.5 几何与 Draw Call

`ArenaLightShow` 用 Cube/Cylinder 拼出约 **150+ 个独立 Renderer**（4 个 sensor × ~20 件、2 个 console × ~15 件、inspection rail ~20 件、24 个 index tab…）。这些静态件完全可以按材质合并网格，4 种材质 → 4 个 draw call。

已有实测：draw 138-628、三角峰值 79-211 万、RTX 5090 上 59.99-60 FPS。高配没问题，但**没有低端机数据**。

排序：**先治"读起来像灰模"，再治打击感，最后动性能**。视觉收益/风险比从高到低。

| 1 | **贴图按类压缩 + 平台分级 + 开 mip streaming** | `Assets/Editor/ArenaArtBudget.cs`（已写，菜单执行） | 显存 1.3 GB → 目标 < 400 MB；移动端首次可用 |

## 7. 一个技术美术视角的提醒

这个项目的工程纪律（每版三分辨率实拍、逐笔 provenance、射线净空审计）比多数商业项目都强，短板不在"做事不认真"，而在**没有一份先于生产的预算表**——所以出现了 30,000 三角顶格无余量、`width_m` 全项目无核验、贴图 4096 未压缩无平台分级这类"单个决定都合理、堆起来失衡"的情况。

技术美术在这里最有价值的产出不是某个 shader，而是**让下一个资产在被制作之前就知道上限**。第 2 节那张表就是为此准备的，建议把它落到 `docs/美术资产规范.md` 并让每个新资产在导入时过一遍 `ArenaArtBudget` 的审计。
