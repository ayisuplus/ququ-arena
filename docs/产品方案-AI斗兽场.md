# AI斗兽场（QuQuArena）产品方案

> 全民电子蛐蛐时代的基础设施：把任何脑洞变成「蛐蛐罐」，把大模型拉进去斗，自动生成排行榜与战报。

---

## 1. 产品背景与灵感

源自一次关于「Benchmark 产业化」的讨论，核心洞察：

1. **Benchmark 已从评估工具演化为独立的论文生产范式**。套路高度成熟：定义一个没测过的能力 → 收题 → 跑模型 → 发现"现有模型仍有巨大不足" → 发榜发论文。
2. **"做一个 benchmark" 的门槛正在崩塌，但"做一个好 benchmark" 依然稀缺**。未来值钱的 benchmark 取决于：任务重要性、区分度、抗污染、测到真能力、能否形成研究方向。
3. **Benchmark 正在从学术评测演化为 AI 时代的竞技娱乐——"全民电子蛐蛐"**：网友出题、组题库、做 leaderboard，模型公司盯着民间榜单调模型。出 benchmark 的成本会越来越低："帮我设计一个测四川话阴阳怪气的 benchmark，跑 20 个模型"——当晚排行榜就出来了。
4. **未来会出现"problem inventor（问题发明者）"这个新角色**：脑洞大、观察细、善于发现模型盲区的人，不需要几千张 GPU 也能做有影响力的研究。

**问题**：今天想把一个脑洞变成一场"斗蛐蛐"，仍然要自己写评测脚本、对接各家 API、统计分数、画图做榜。流程琐碎，劝退了大量"脑洞多但不想写胶水代码"的人。

**AI斗兽场要做的就是这件事**：把"脑洞 → 蛐蛐罐 → 开赛 → 榜单/战报"变成一条流水线。

---

## 2. 核心定位

> **AI 时代的"蛐蛐罐工厂 + 斗兽场"**：一个以通用 Agent 为底座的 Benchmark 创作与对战平台。
> 上承"problem inventor"的脑洞，下接几十个大模型 API，中间用 Agent 自动完成出题、跑题、裁判、排名、写战报。

一句话：**让"卧槽，所有模型在这个场景里都很蠢"到"排行榜出来了"的时间，从两周缩到十分钟。**

### 与现有产品的差异

| 维度 | 传统评测框架（lm-eval-harness 等） | LMArena 类对战平台 | **AI斗兽场** |
|---|---|---|---|
| 面向谁 | 工程师 | 围观群众投票 | **问题发明者（脑洞玩家）+ 研究者** |
| 核心动作 | 跑现成 benchmark | 匿名 1v1 投票 | **发明新蛐蛐罐 + 多模型开赛** |
| 题目来源 | 官方数据集 | 用户临时提问 | **Agent 协助系统化生成 + 人工打磨** |
| 产物 | 分数 | 排行榜 | **排行榜 + 可引用的战报 + 失败案例分析** |
| 气质 | 严肃工具 | 娱乐围观 | **学术含金量 × 斗蛐蛐的乐子** |

## 3. 目标用户与使用场景

### 目标用户

1. **脑洞玩家 / 民间 AI 行为学家**：天天跟模型玩，总能发现模型的奇怪盲区，想把观察变成一场"比赛"分享给大家。
2. **problem inventor / 研究生**：需要快速验证一个 benchmark 想法的 pilot（如错别字容错、拼音理解），先跑通小样本再决定要不要扩成论文。
3. **模型团队 / 厂商**：想快速知道自家模型在某细分能力上的相对位置。
4. **围观群众**：看排行榜、看"名场面"（模型翻车案例），找乐子。

### 典型使用场景

- **场景 A：脑洞变蛐蛐罐**。输入一句话："测一下大模型懂不懂四川话阴阳怪气"。出题官 Agent 自动生成维度划分（反讽识别 / 语气强度 / 语境适配 …）、题目样例与评分规则，人工增删后成一个标准「蛐蛐罐」。
- **场景 B：开赛斗蛐蛐**。选一个蛐蛐罐 + 若干模型（GPT / Claude / DeepSeek / Kimi / 开源模型 / 本地模型），一键并发跑题，裁判自动评分。
- **场景 C：看榜与复盘**。生成排行榜（总分、分维度、Elo 评级）与 HTML 战报，自动摘录"名场面"——模型集体翻车的题目。
- **场景 D：pilot 研究**。研究者把自己的数据集（如 TongJia-Bench 拼音剖面）转成蛐蛐罐格式，10 分钟拿到多模型对比初稿，决定研究方向。

## 4. 产品架构设计

### 4.1 总体分层（基于 pi Agent 底座构建）

```
┌─────────────────────────────────────────────────────┐
│                   交互层（本 MVP）                    │
│   CLI（list / battle / invent） + HTML 战报           │
│   （后续：Web 斗兽场、实时围观、分享链接）              │
├─────────────────────────────────────────────────────┤
│                   斗兽场业务层                        │
│  ┌───────────┐ ┌──────────┐ ┌─────────┐ ┌────────┐ │
│  │ 蛐蛐罐管理  │ │ 对战引擎  │ │ 裁判团   │ │ 排行榜  │ │
│  │ Arena     │ │ Runner   │ │ Judge   │ │ Board  │ │
│  └───────────┘ └──────────┘ └─────────┘ └────────┘ │
│  ┌─────────────────────────────────────────────────┐│
│  │ 出题官 Agent（Problem Inventor）——脑洞 → 蛐蛐罐    ││
│  └─────────────────────────────────────────────────┘│
├─────────────────────────────────────────────────────┤
│              pi 通用 Agent 底座（earendil-works/pi）   │
│  @earendil-works/pi-agent-core  Agent 循环 / 工具调用  │
│  @earendil-works/pi-ai          统一多厂商 LLM API    │
│   （OpenAI / Anthropic / Google / DeepSeek / Moonshot │
│     / Qwen / OpenRouter / Ollama / 任意 OpenAI 兼容） │
├─────────────────────────────────────────────────────┤
│              数据层                                  │
│  蛐蛐罐包（arena.json + tasks.jsonl，Git 友好）        │
│  战绩库（results/*.json + 战报 HTML）                  │
└─────────────────────────────────────────────────────┘
```

### 4.2 模块划分

| 模块 | 职责 | 对应代码 |
|---|---|---|
| **蛐蛐罐（Arena）** | 一个可移植的 benchmark 包：`arena.json` 元信息 + `tasks.jsonl` 题目 + 评分规则声明。借鉴 TongJia-Bench 的 schema（id/track/condition/input/target/meta），支持按 condition 分维度统计 | `src/types.ts` `src/arena-loader.ts` |
| **蛐蛐登记处（Model Registry）** | 统一抽象"参赛蛐蛐"。真实模型走 pi-ai 的多 provider 通道；无 API Key 时提供内置 mock 蛐蛐（不同"性格/战力"的虚拟模型）保证全流程可演示 | `src/models.ts` `src/mock.ts` |
| **对战引擎（Runner）** | N 模型 × M 题的并发执行、失败重试、用量与耗时统计 | `src/runner.ts` |
| **裁判团（Judge）** | 可插拔评分：`exact`（标准化精确匹配）、`contains`、`regex`、`llm-judge`（用强模型按 rubric 打分，走 pi-ai） | `src/judge.ts` |
| **排行榜（Leaderboard）** | 总分 / 分维度（condition）准确率 /  pairwise Elo 评级 | `src/leaderboard.ts` |
| **出题官 Agent（Inventor）** | 基于 pi-agent-core 的 Agent：接收一句脑洞，通过工具调用产出结构化蛐蛐罐（维度设计 → 出题 → 评分规则 → 落盘）。无 Key 时退化为模板生成器 | `src/inventor.ts` |
| **战报（Report）** | 生成单文件 HTML 战报：榜单、分维度对比、Elo、名场面（集体翻车题）、逐题明细 | `src/report.ts` |
| **CLI** | `arena list / battle / invent` 三个命令覆盖核心交互流程 | `src/cli.ts` |

### 4.3 关键设计决策

1. **蛐蛐罐即数据包，而非代码**。题目与评分规则都是声明式数据，可 Git 管理、可分享、可引用——这是"benchmark 能形成研究方向"的工程前提。
2. **裁判可插拔**。学术向任务用 exact match 保证可复现；开放任务用 LLM-judge + rubric；后续可加"双裁判 + 仲裁"抗偏差。
3. **mock 蛐蛐是一等公民**。没有 API Key 也能完整体验"造罐→开赛→出榜"，降低上手门槛，也方便 CI 测试。
4. **Agent 只负责"发明"，不负责"裁判公正"**。出题官可以用 Agent 放飞想象力，但评分逻辑必须落在可复现的规则上——对应论文里"题目有效性、评分可靠性"的要求。

## 5. MVP 范围与后续路线

### MVP（本次交付）
- 蛐蛐罐格式 v0.1 + 加载校验
- 三个内置蛐蛐罐：**TongJia 拼音剖面**（复用 TongJia-Bench pilot 真实数据）、**阴阳怪气大师**（LLM-judge 演示）、**首字母缩写悬崖**（复现 TongJia 最有传播度的发现）
- battle 全流程：多模型跑题 → 裁判评分 → 排行榜 → HTML 战报
- 出题官 Agent（有 Key 走 pi-agent-core，无 Key 走模板）
- mock 蛐蛐离线演示模式

### 路线图
- **v0.2**：Web 斗兽场（实时围观、进度条、名场面条幕）；抗污染检查（题库撞库检测）；双裁判仲裁
- **v0.3**：蛐蛐罐市场（发布/ fork / 引用他人蛐蛐罐）；赛季与段位；战报一键转论文 LaTeX 骨架（experiment section 自动生成）
- **v1.0**："problem inventor"社区——榜单权威性来自题目质量评分与复现率，而不是嗓门
