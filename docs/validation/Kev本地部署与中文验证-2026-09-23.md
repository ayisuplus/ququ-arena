## 0. 一句话结论

> **能用，但不能单独当裁判。** Kev-4B 在本机成功跑起来（RTX 5090 / sm_120 / torch cu128），中文**没有崩**：
> 「明显答对」11/11 全对、「意思对但用词不同」8/8 全对 —— **恰好是原来 regex 误杀的那一类，Kev 判得全对**；
> 但**「明显答错」只挡住 8/12（67%）**，会把「顺着陷阱作答」「差一个字的成语」「另一部电影名」判成"答对"。
> 建议：**Kev 作为多裁判团中的一票 + 严格规则兜底，而不是唯一裁判**；不建议直接替换现有 LLM 裁判。
> 延迟 ~0.12–0.17s/题（单题）、11–16ms/题（打包 31 题），**比远程 API 裁判快约两个数量级**，裁判成本归零成立。
>
> **另两个工程要点**：① `flash-linear-attention` 在本机（Windows + sm_120）**装了会把服务打挂**（首个请求永不返回），必须**不装**；
> ② `KEV_MERGE=0` 能让显存从 **18.5 GB 降到 9 GB**，且判定结果逐题不变 —— 建议作为生产默认（详见 §2.5 / §2.6）。

## 2. 部署实录

### 2.1 实际命令（可复现）

```bash
# 1) 环境（Python 3.12；Kev requires-python >=3.12,<3.14）
uv venv /e/kev-eval2/.venv --python 3.12

# 2) 依赖（Tsinghua 镜像）
uv pip install --python /e/kev-eval2/.venv/Scripts/python.exe \
  "transformers>=5.17,<6" "peft>=0.21" "accelerate>=1.15.0" \
  "fastapi>=0.115" "uvicorn>=0.30" "pydantic>=2.9" numpy safetensors

# 3) torch CUDA 轮子（关键：Windows 必须显式装 cu128）
uv pip install --python .../python.exe --index-url https://download.pytorch.org/whl/cu128 \
  --no-deps "torch==2.8.0+cu128"

# 4) 启动（HF_HOME 指向预热好的缓存，离线运行；KEV_MERGE=0 省一半显存；不装 FLA，见 §2.5）
cd /e/kev-eval2
HF_HOME=E:/hf-cache HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 KEV_MERGE=0 \
  /e/kev-eval2/.venv/Scripts/python.exe -m kev.serve --run E:/kev-models/kev-4b --port 8009
```

> ⚠️ **不要** `uv pip install flash-linear-attention`：本机会挂死首个推理请求（§2.5 实测）。

> 说明：官方是 `uv sync --extra serve` + `--run jaredpalmer/kev-4b`（走 HuggingFace）。
> 因本机 **Xet CDN 被封**，改为「仓库源码落本地 + 权重灌进 HF 缓存 + `--run <本地目录>`」，**语义完全等价**。

### 2.5 `flash-linear-attention` 坑（⚠️ 本机结论：装了会更糟，必须**不装**）

README 说 CUDA 上需装 `flash-linear-attention`（Qwen3.5 的 DeltaNet 层）。实测走完了全过程，**结论与 README 相反**：

| 步骤 | 结果 |
|---|---|
| `uv pip install flash-linear-attention` | ✅ 装上 `flash-linear-attention==0.5.2` + `fla-core==0.5.2`（纯 Python，**无编译过程**） |
| `import fla.ops...` | ❌ `ModuleNotFoundError: No module named 'triton'` |
| `uv pip install triton-windows` | ✅ 装上 `triton-windows==3.8.0.post28`，`import triton` 成功 |
| `from fla.ops.gated_delta_rule import chunk_gated_delta_rule` | ✅ 成功，但**首次 import 耗时 72.7 s**（Triton JIT） |
| 装上 FLA 后**重启服务** | ✅ 服务起得来，`GET /v1/models` 200 |
| **装上 FLA 后发第一个 `/v1/systemone`** | ❌ **挂死**：日志只打印 Triton 编译 `remark: l2norm.py` 后停住，**>4 分 33 秒无响应**，且 `GPU 利用率 = 0%`（不是"在算"，是**卡住/死锁**） |

→ **本机（Windows + sm_120 + triton-windows 3.8.0）上，FLA 的 DeltaNet Triton kernel 会挂死首个推理请求，实际不可用。**
最终处置：**卸载 `flash-linear-attention` / `fla-core` / `triton-windows`**，回到无 FLA 的路径。

**为什么无 FLA 反而没问题**：transformers 5.17 的 Qwen3.5 DeltaNet 走
`@use_kernel_func_from_hub_with_fallback("chunk_gated_delta_rule", "fla")`，优先级为
`Hf kernels → 原包(fla) → 纯 Torch 路径`。**无 FLA 时自动落到纯 Torch 参考实现，服务正常、无报错**，
唯一的代价是 `causal_conv1d_fn` / `chunk_gated_delta_rule` 各打印一条"falling back ... much slower"提示。
**本机实测（纯 Torch 参考路径）性能完全够用**（见 §4：单题 122ms、打包 11ms/题），
所以 **FLA 在本机是"net negative"：装了不但不快，还把服务打挂**。

> ⚠️ 这是**本机环境特有**的结论（Windows + sm_120 + triton-windows）。Linux + H100 上 FLA 应正常且更快（README 的 H100 数字就是这么来的）。**但本项目部署在本机，就以"不装 FLA"为准。**

### 2.6 显存占用（含关键优化：`KEV_MERGE=0` 省一半显存）

| 配置 | 显存（总量 / 其中模型） |
|---|---|
| 桌面基线 | ~5.5 GB（杀进程后实测回收至 5.7 GB） |
| 默认 `KEV_MERGE=1` | **24201 MiB（模型本体 ≈ 18.5 GB）** |
| **`KEV_MERGE=0`** | **≈ 13155 MiB（模型本体 ≈ 7.5–9 GB）** |

> 默认 `KEV_MERGE=1` 会先把 LoRA 以 **fp32** 合并再转 bf16，故显存翻倍；`KEV_MERGE=0` 直接 bf16 加载。
> **关键实测：`KEV_MERGE=0` 的判定结果与默认配置逐条一致**——重跑中文 `noul` 全部 31 题，
> 准确率同为 **27/31**、**错误题号与概率值几乎完全相同**（如 `rz-fp01-wrong` 0.991 vs 0.991、
> `rz-ab01-para` 0.62 vs 0.63），且略快（15.8ms/题 vs 22.7ms/题）。
> → **`KEV_MERGE=0` 是"白捡的省显存"，建议作为本项目默认**（32GB 卡还要给 3D 客户端留地方，18.5GB 太满）。

## 3. 中文验证结果（本任务核心）

### 3.1 测试设计

用**项目真实趣味题**（`arena/arenas/*/tasks.jsonl` 的题面/参考答案），构造 31 组
`(题目, 考生答案, 标准答案)`，分三类：

- `correct_obvious`：明显答对（11 组）
- `correct_paraphrase`：**意思对但用词不同**（8 组）← **原 regex 误杀的那一类，换判法的核心价值**
- `wrong`：明显答错（12 组，含「顺着陷阱字面作答」）

对同一批题，分别用 Kev 的三种问法：`noul`（是否答对）、`choice`（答对/答错二选一）、`score`（0-2 分）。

### 3.2 结果总表

| 问法 | 明显答对 | 意思对但用词不同 | 明显答错 | **总准确率** |
|---|---|---|---|---|
| `noul`（yes/no） | **11/11 (100%)** | **8/8 (100%)** | 8/12 (67%) | **27/31 = 87%** |
| `choice`（二选一） | 11/11 (100%) | 7/8 (88%) | 9/12 (75%) | **27/31 = 87%** |
| `score`（0-2 分） | 11/11 (100%) | 6/8 (75%) | 4/12 (33%) | **21/31 = 68%** |

### 3.3 关键结论

**✅ 正面（决定"能不能用"）**
1. **「意思对但用词不同」这一类，`noul` 问法 8/8 全对**。例：
   - 参考「那时我还没出生」 vs 考生「因为你当时还在妈妈肚子里，根本还没来到这个世界上呢」→ **判对** ✅
   - 参考「给别人理发是剪别人的头发」 vs 考生「理发师只是给顾客剪头发而已，他自己那颗头没人动」→ **判对** ✅
   - **这正是原来 regex/exact 判分误杀、导致 5 个趣味罐停战的根因，Kev 恰好解决了它。**
2. **「明显答对」三类问法都 11/11 全对**，识别正确回答很稳。
3. **中文能力没有"崩"**：模型能读懂中文题干与中文答案的语义。
4. **置信度是双峰的**：判对时 p≈0.93–0.99，判错时 p≈0.03–0.15 —— 不是"模棱两可"，而是"有把握地对/有把握地错"。

**❌ 负面（决定"能不能单独用"）**
5. **「明显答错」漏判率高**：`noul` 只挡住 8/12，**4 个错答被判成"答对"**，且**置信度极高**（p=0.95–0.99）：

   | 题目 | 标准答案 | 考生错答 | Kev 判定 |
   |---|---|---|---|
   | 爸妈结婚为啥没请我喝喜酒 | 那时我还没出生 | 「因为他们觉得小孩子不能喝酒」 | **答对 p=0.99** ❌ |
   | 近视为啥老了不会老花 | 近视和老花可并存 | 「因为眼睛适应了近视度数」（顺着陷阱） | **答对 p=0.89** ❌ |
   | 🦊🐯💪 猜成语 | 狐假虎威 | 「狐朋狗友」 | **答对 p=0.99** ❌ |
   | 🛳️🧊💔 猜电影 | 泰坦尼克号 | 「加勒比海盗」 | **答对 p=0.77** ❌ |

   → 失败模式有共性：**只共享个别字词、或顺着题目错误前提作答时，Kev 区分不出"结论不同"**。
6. **`score` 问法最差（68%）**：它对"沾边但没抓住要点"过于宽容，12 个错答里 8 个落在"沾边"档。

### 3.4 两个对照实验（判断这是不是"中文的锅"）

**对照 A：英文同构题（判断是否中文特有）**

| | 明显答对 | 意思对用词不同 | 明显答错 | 总计 |
|---|---|---|---|---|
| 英文 `noul` | 6/6 | 4/4 | **4/7 (57%)** | 14/17 (82%) |

→ **英文的错答漏判率和中文一样糟**。结论：**"错答漏判"不是中文能力问题，而是 Kev 的先天属性**——
它是被训练来做「固定选项分类/路由」的（训练集是英文客服工单 `decision-v7`），
**不是为"开放式答案语义等价判定"设计的**。拿它做开放题裁判，本身就超出它的训练分布。

**对照 B：中文 + 更严格的指令（判断能否靠提示词修好）**

| | 明显答对 | 意思对用词不同 | 明显答错 | 总计 |
|---|---|---|---|---|
| 中文 `noul` + 严格指令 | 11/11 | 8/8 | **9/12 (75%)** | 28/31 (90%) |

→ 严格提示词**略有改善**（错答 8/12 → 9/12），但**治标不治本**：
`raz-fp01-wrong`、`rz-fp05-wrong`、`eq-id08-wrong` 三个"自信错判"依然存在。
**靠 prompt 修不好，这是模型能力边界。**

## 4. 性能实测

单调用方、服务端一把锁（串行）下的实测：

| 场景 | 延迟 |
|---|---|
| 单题（状态各不相同，n=20） | **p50 = 121.6 ms**，mean 119.4，min 106.5，max 135.2 |
| 同一状态重复问（前缀缓存命中） | **p50 = 74.6 ms** |
| **打包 31 题一次请求**（状态 ~2013 tokens） | **347 ms 总计 → 11.2 ms/题** |
| 同一打包请求重放（前缀缓存） | 197 ms |
| 显存（默认 `KEV_MERGE=1`） | 24.2 GB（含桌面 5.5GB），模型本体 ~18.5 GB |
| 显存（**`KEV_MERGE=0`，推荐**） | ~13.2 GB（含桌面），模型本体 ~7.5–9 GB |
| 中文 31 题打包（`noul`，`KEV_MERGE=0`） | 491 ms → 15.8 ms/题 |

> 上表均为**不装 FLA**（纯 Torch 参考路径）的数字——装了 FLA 反而挂死（§2.5）。**纯 Torch 路径已完全够用**。
> 前缀缓存统计：`hits=12, misses=27, cached_states=4`（`KEV_PREFIX_CACHE` 默认 4）。
>
> **重复测量与方差（诚实话）**：同一配置重跑，单题 p50 会从 **121.6 ms 漂到 164.7 ms**、打包 31 题从 **11.2 漂到 16.1 ms/题**、
> 中文打包从 15.8 漂到 33.2 ms/题。差异来自**同卡并发占用的其它 GPU 程序**（浏览器 / 桌面应用），不是配置差异。
> **结论请按量级读："单题 ~0.12–0.17 s、打包 ~11–33 ms/题"**，不要抠到小数点——不影响"比远程裁判快两个数量级 + 成本为 0"的判断。

### 与既有裁判的量级对比

| 方案 | 单题延迟 | 成本 | 来源 |
|---|---|---|---|
| **本地 Kev-4B (RTX 5090)** | **~0.12 s**（打包 11 ms/题） | **0**（电量） | 本报告实测 |
| 硅基流动（团队此前实测） | 27.7 s / 33.3 s | 按 token 计费 | team-lead 提供 |
| 远程 API judge | 秒级 | 按 token 计费 | 项目现状 |

## 5. 接入方案（本轮只出方案，未改生产代码）

### 5.1 现状与鸿沟

- 项目裁判：`arena/src/judge.ts`，`JudgeSpec` 支持 `exact / contains / regex / llm / rubric / all / any / not`；
  `llm` 裁判走 `oneJudgeVote()` → `askModel()` → **OpenAI 兼容 `/chat/completions`**，要求模型返回
  `{"score": <number>, "reason": "<string>"}` JSON。
- Kev：**System One API（`POST /v1/systemone`）**，输入 `noul/choice/score` 问法，输出概率，**不生成文本、不产 JSON**。
- **两者协议不通**，且**语义模型不通**（Kev 不会"按 rubric 写评语"，只会给概率）。

### 5.2 接入方案：两阶段（Phase 1 零改 src → Phase 2 可选的一等公民）

读完 `judge.ts` / `models.ts` / `model-settings.ts` 后的关键事实：

- 裁判链路 `judgeAnswer → evalSpec → llmJudge → oneJudgeVote → askModel(judge,…)`，
  其中 `judge = resolveContestant(judgeModel)`。**只要 `judgeModel` 是 `custom:xxx`，就会走
  `settings.custom` 里的 `CustomModel{baseUrl,apiKey,modelId,stream}` → `askCompatible()` → `${baseUrl}/chat/completions`。**
- 即：**现有的 `custom:` 渠道本身就已经是一条"任意 OpenAI 兼容端点"的裁判通道**，只是 Kev 说的是 System One，不是 OpenAI。

#### Phase 1（推荐先做）：写一个"协议翻译 shim"，用现有 `custom:` 渠道接入 —— **零改动 `arena/src`**

```
arena/scripts/kev-openai-shim.mjs   （新文件，不是 src 生产代码）
   POST /chat/completions  ←  OpenAI 形状，收 judge.ts 拼好的 prompt
        ↓ 解析出【题目】【参考答案】【考生回答】【满分】
        ↓ 拆成 Kev 的 System One 问法（见下）
   POST http://127.0.0.1:8009/v1/systemone
        ↓ 把概率折算成 0..scale
   ←  {"choices":[{"message":{"content":"{\"score\":N,\"reason\":\"…\"}"}}]}
```

- 注册进 `.local/model-settings.json`（**已被 `.gitignore` 覆盖**）：
  `{ "id":"custom:kev", "name":"Kev-4B(本地)", "baseUrl":"http://127.0.0.1:8010/v1", "modelId":"kev-latest", "stream":false, "apiKey":"local" }`
- 然后：`--judge custom:kev`，或与远程裁判并肩 `--judge custom:kev,deepseek:deepseek-v4-flash`。

**这一版的全部好处都来自"不碰 src"**：
1. `askCompatible` 的重试 / 用量解析 / 错误分类**全部白拿**；
2. **多裁判机制白拿**：`llmJudge` 已支持多裁判取均值 + 公开分歧度（`dispute`/`votes`）——Kev 直接当其中一票，
   **分歧度高时自动降级到远程 judge 复核**，正好对上 §3.3 "Kev 会漏判" 的缺陷；
3. `custom:` 渠道本来就支持 `stream:false`（`askCompatible` 只在 `opts.onDelta && endpoint.stream` 时才走 SSE），
   而裁判路径 `oneJudgeVote` **不传 `onDelta`**，天然非流式，与 Kev 单次前向完美契合。

**shim 内部的判分映射（用本次实测选出的最稳形态）**：
把 rubric 拆成**若干 `noul` 子问题**（一个请求打包，11ms/问），而不是让 Kev 直接打 `score`——
实测 `score` 形态最差（68%），`noul` 最稳（87%）。例如 `ruozhiba` 的 rubric 可拆成：
`①是否点破了题面的错误前提？ ②正解是否与参考答案语义一致？`，两者皆 yes 才给满分。
这样既贴合 rubric 结构，又绕开 Kev 不擅长"连续打分"的弱点。

#### Phase 2（可选，若 Phase 1 跑出价值）：提升为一等公民 `kev` 裁判

在 `src/types.ts` 的 `JudgeSpec` 加 `{ kind:'kev'; rubric:string; scale?:number; baseUrl?:string }`，
`src/judge.ts` 的 `evalSpec` 加 `case 'kev'`，**不再经过 `askCompatible`**，直连 `/v1/systemone`。
好处：少一个进程、语义最诚实（Kev 本就不是 chat 模型）、可用 `/v1/systemone/separate` 与 `/permute`。
代价：动 `src`（`types.ts` + `judge.ts`）+ 单测。

> 说明：`JudgeSpec` 里已声明 `{ kind:'rubric'; dimensions }`，但 `src/judge.ts` 的 `evalSpec` **并没有实现它**
> （会落到 `default` → `ruleJudge` 抛错）。若走 Phase 2，可考虑顺手把 `rubric` 也补齐，或直接让 `kev` 分支承担这部分。

**无论哪一阶段，都必配"严格兜底"**（§3.3 结论：Kev 会漏判 33% 的错答）：
`{ kind:'all', judges:[ <严格规则：排斥性实体/精确成语匹配>, <kev 语义等价> ] }`——
规则裁判一票否决"差一个字的成语 / 另一部电影名"，Kev 负责宽容"意思对但用词不同"。

## 6. 未验证与边界（诚实清单）

1. **未测 Kev-0.8B / 9B**：只验证了 4B（符合任务要求）。更大模型（9B）在错答判别上大概率更好（README 显示 9B 准确率更高），**但没有实测，不下结论**。

3. **未测 `permute`（选项顺序偏置）**：`choice` 问法的顺序敏感性未测。

5. **FLA 加速已实测，结果是"不可用"**（详见 §2.5）：装上 `flash-linear-attention + triton-windows` 后首个推理请求挂死（>4.5 分钟无响应、GPU 0%），已卸载回到纯 Torch 参考路径。**因此"FLA 能带来多少加速"这个问题在本机无从测得**——本机根本没有可用的 FLA 路径。Linux/H100 上 FLA 的加速幅度仍属未验证。
6. **未测并发**：Kev 服务端**单请求串行（一把锁）**，多人同时评测会排队，**吞吐上限未测**。
7. **中文样本量小**：31 组（错答 12 组）足以看出模式，但**统计置信区间宽**；「错答漏判 ~67%」这个数字的误差范围不小。
8. **英文对照样本更小**（17 组），"英文同样差"的结论方向可信、量级不可过度解读。
9. **未验证中文微调能否修好**：README 明确说"换语言建议短微调"，**用一个几百条中文判分样本微调 Kev，很可能显著改善错答漏判** —— 这是最有希望的方向，但**本轮未做**。
10. **`score` 问法为何最差、是否有更优的问法设计**（如拆成两个 noul、或给更细的 legend）未做系统搜索。
