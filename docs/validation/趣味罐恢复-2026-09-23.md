## A 类实现说明

### 判定闸门的机制（`arenaloader.ts:112` 即 `src/arena-loader.ts`）

```ts
export function playableTasks(def: ArenaDef, tasks: ArenaTask[]): ArenaTask[] {
  if (def.review?.blockedReason) return [];          // ← 整罐停战闸门
  return tasks.filter((task) => !Object.hasOwn(def.review?.excluded ?? {}, task.id));
}
```

`review.blockedReason` 存在即整罐 `playableTasks` 返回空数组，`requirePlayableTasks`（开赛入口）随即抛「暂停对战」。**解除方式 = 移除该键**；原停战理由按项目「诚实留痕」要求**转存到 `review.note`**（`validateArena` 第 95 行允许 `note` 非空字符串），并保留 `review.date`，另附本轮「已改用 LLM 裁判」的处置说明，全程可追溯。

### 判分改成什么（复用了既有机制，未新发明）

直接复用项目已有裁判机制 `src/judge.ts` 的 `{kind:'llm', rubric, scale}` 分支（v2 起支持 `--judge a,b` 多裁判仲裁、分歧度公开）。A 类三罐只把**罐级/逐题规则裁判**换成 **llm 裁判**：

- 每题仍带 `target` 参考答案，作为 rubric 的语义参照——但 rubric 明确要求「参考答案不是唯一合法措辞，等价说法同样满分」，正是综艺语境下「答案不唯一」由缺陷转为玩法本身。
- 评分 `0..scale`（本处 scale=10）经归一化为 `0..1`；多裁判取均值并记录 `dispute`。

## 成本估算（用户明确「不要用我的 mimo pro，它烧钱很快」）

**裁判调用次数是确定性的**：每「题 × 选手」记录调用一次裁判，多裁判（`--judge a,b`）再乘裁判数。

```
裁判调用次数 = N_题 × M_选手 × J_裁判数
```

三罐单场调用次数（每题净一闸）：

| 罐 | N 题 | M=4 选手 × 1 裁判 | × 2 裁判（`--judge a,b`） |
|---|---|---|---|
| `ruozhiba` | 16 | 64 | 128 |
| `riddle-me` | 16 | 64 | 128 |
| `case-clash` | 24 | 96 | 192 |
| **三罐合计** | 56 | **224** | **448** |

**单次裁判调用的 token 量**（估算）：system 指令 ≈ 180 tok + rubric ≈ 120–250 tok + 题面 ≈ 30–120 tok + 参考答案 ≈ 10–40 tok + 考生作答 ≈ 50–150 tok → 输入 ≈ **450–900 tok**；输出为一行 JSON（`{"score":..,"reason":".."}`）≈ **40–80 tok**。按输入 700 / 输出 60 估：三罐单场（224 次）× 760 ≈ **输入 ~157k tok、输出 ~13k tok**；双裁判（448 次）约翻倍。
