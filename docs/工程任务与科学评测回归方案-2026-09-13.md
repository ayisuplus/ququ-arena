# 工程任务与科学评测回归方案

状态：现状核查与建议，尚未实现工程任务执行器。用户已明确工程性优先指向“真实工程任务：写代码、跑测试、交付产物”。保留桌面端和已认可的竞技视觉。

实施进展：按用户后续“开始施工”完成了首版工程实验台、6 个任务与 Codex 真实执行闭环。实现、验证证据和当前服务加载限制见 [工程实验台：实现与验收](./工程实验台-实现与验收-2026-09-13.md)。下文保留提案时的现状记录。

## 1. 产品主线

建议定位为 **可观战的 AI 工程实验室**：提出任务 → 固定仓库与验收条件 → Agent 独立执行 → 检查真实产物 → 比较能力与可靠性。观赛展示这条链路的真实进展。

工程性体现在能交付可运行的修改，科学性体现在能解释这次结果测量了什么、哪些条件相同、结论有多大不确定性。竞技综合分继续服务观赛，工程验收结论和研究比较有独立口径。

当前三类文本赛道继续保留。新增的工程任务运行 Agent 的自主工具循环，与已有 2–5 个预编排文本轮次分别建模。

## 2. 已核实的基础与缺口

| 已有代码 | 当前边界 | 下一步价值 |
| --- | --- | --- |
| `diff.ts`、`stats.ts`、CLI `repeat`、`analyze.ts` | 已有配对对比、重复运行和题目诊断，网页主导航只有对战、模型战绩、战报档案 | 把比较、重复实验、任务诊断带入实验主流程 |
| `task-runner.ts`、`models.ts` | 多轮任务携带各自文本历史，尚不改文件、运行构建或生成项目产物 | 单独增加工程运行器，保留文本赛道行为 |
| `agents.ts`、`agent-session.ts` | Codex/Claude 目前用于只读、禁用工具的解说和评分 | 复用协议解析和进程管理；参赛执行配置与只读裁判配置分开 |
| `live-state.ts`、时间轴、回放、失败补评 | 已有完整输出恢复和赛事记录 | 增加命令、文件变更、验收、产物事件 |
| `performance.ts` | 70/15/10/5 竞技权重，速度/Token 还依赖同场参赛者的相对值 | 工程主结论使用任务完成和可靠性，资源指标独立展示 |
| 题库编辑、备份、指纹 | 能冻结材料和规则；缺少工程仓库、环境、工具版本及验收器的完整协议 | 扩展为工程任务包与运行清单 |

本轮用合成数据直接调用现有函数，确认了三处不能靠界面增强解决的问题：

1. `diffBattles` 对相同题库指纹、更换了裁判身份的两场仍允许比较；没有完整比较协议检查。任一战绩缺少指纹时，也不会因缺失而拒比。
2. `bootstrapCI([1])` 返回 `[1,1]`。这是单个观测的退化重采样结果，不能在页面上解释为已精确测得总体能力。
3. 两组始终相差 0.4 的裁判分数得到 `pearson=1`、`meanDispute=0.4`。相关性不能单独支撑“评分一致”。代码虽同时保存分歧，但一些文案把相关性、稳定性与可信度混为一谈。

另查到 `analyzeArena` 按题库名称收集历史、按 taskId 聚合，未按题库指纹和裁判配置分组；人类编辑题目之后，相同题号可能混入不同版本的观测。应先修复分组口径，再展示为科学诊断。

旧方法学中“同裁判同题同答案可复现”“排名高度稳定即结论可信”等表述需要收紧。固定统计随机种子只保证同一份已保存数据重新生成报告一致，不保证模型再次运行答案相同。

## 3. 第一个工程赛道：仓库修复

先支持固定 Node/TypeScript 环境中的小型真实项目任务。每个选手从完全相同的基线开始，独立读代码、修改、执行测试并提交补丁。首个样板题可用“修复重复提交导致的重复入账，同时保持原有行为”，覆盖异步流程、持久化和回归检查。

一个工程任务包包含：

- 需求与可观察验收条件；仓库快照/提交和依赖锁定文件。
- 可编辑范围、可用工具、环境版本、时间与调用预算。
- 可见的开发测试，以及由验收器独立持有的测试与最终状态检查。
- 允许交付的文件、补丁和启动方式；题目来源及人工审查状态。

默认建议先按每任务 15 分钟设计工程预算，再通过样板实测调整。文本题 60 秒或每轮 3 分钟的超时规则不直接套用。模型 API 重试与 Agent 正常的“测试失败 → 修改 → 重测”分别计数；测试变红是工程过程，不能直接算一次模型调用失败。

**验收顺序**：保存提交补丁 → 停止选手执行 → 将允许的修改应用到干净基线 → 用固定依赖和可信验收器重新运行 → 保存结论与证据。既要证明目标问题得到修复，也要检查原来通过的行为仍通过。选手自己输出“测试全绿”不能替代正式验收。

验收不按代码行数、日志中的 PASS 字样或可任意删除的测试数量计分。允许不同实现；禁止通过修改验收器、跳过构建或删测试获得成功记录。每次提交保留 `patch.diff`、测试输出、构建日志、产物清单及摘要哈希。

故障至少区分环境准备失败、模型服务失败、Agent 未完成、产物验收失败。报告同时给出环境有效样本数与端到端交付成功率，不能静默剔除大量失败后只展示剩余成功者。

本机已发现 Docker、WSL、Git 和 Node；但本轮 `docker version` 无法连接 Docker Desktop Linux Engine。容器环境尚未就绪，未启动或更换其他服务。Git worktree 只隔离代码副本，不等于安全沙箱。工程执行器的第一个技术验收是把原生 Agent 的文件、命令、鉴权与退出行为放进可验证的隔离环境；不能为了跑通而降级成对用户项目的无限权限。

## 4. 科学比较怎么嵌入产品

需要明确两种比较对象：

| 比较方式 | 固定什么 | 结论范围 |
| --- | --- | --- |
| 相同工具执行器接入不同 API 模型 | 工具、提示、环境、预算、任务、验收器 | 在这套执行条件下的模型差异 |
| Codex、Claude Code 等原生 Agent 对比 | 任务、环境约束、预算、验收器；记录各自工具和版本 | Agent 系统的端到端差异，不能归因于底层模型单独的能力 |

每次运行保存任务版本、基线哈希、Agent/模型身份、实际可得的版本、提示和工具定义、依赖与运行时、验收器版本、预算、并发和时间、采样参数及是否由供应商提供。无法取得的字段标为未知，不编造精确可复现性。

实验结论优先展示：任务交付成功率、重复运行的成功情况、功能与回归检查、失败类型、耗时和实际用量。性能比较控制同机资源竞争与冷热启动条件，分别记录环境准备和执行耗时。原始 Token 与缓存率保留为资源观测，不解释为跨服务通用的模型能力。

保留原来的竞技权重和胜负动画，但研究视图不把一次综合分第一写成“模型显著更强”。置信区间、配对差异、样本数量、独立任务数量、重复次数及可比条件一并显示；不同版本任务或不同验收器默认分组。单题和不满足方法前提的样本仅给描述性结果。

科学题库还需要开发集与保留验证集，按任务来源或同源变体成组划分。Agent 根据失败案例学习后，不能再用同一批已看过的任务证明泛化提升。人工金标准用于校准 LLM 评审，模型评审负责可维护性等需要判断的维度；构建和功能是否通过由可执行检查决定。

参考 Anthropic 对 Agent 评估的区分：执行轨迹描述做了什么，最终环境状态说明是否完成；评价原生 Agent 时测量的是模型与工具执行器共同工作的结果。[官方说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

SWE-bench 通过向仓库应用补丁并在固定容器环境运行测试评估问题是否解决，适合借鉴验收机制；首版先用我们能逐题复核的小任务包，不直接声称达到其完整评测标准。[官方验收说明](https://www.swebench.com/SWE-bench/guides/evaluation/)

LLM 裁判存在位置、冗长偏好和自我偏好等已报道问题，匿名、独立会话和原文引用有帮助，但不足以单独证明评分准确。[MT-Bench / Chatbot Arena 裁判研究](https://arxiv.org/abs/2306.05685)

## 5. 用户会看见什么

主导航建议改为 **实验台 / 观赛 / 任务库 / 实验记录**。模型和 Agent 配置从实验台直接可达。实验与观赛共享同一轮运行记录，切换视图不会重复调用。

- 实验台：任务与验收条件、Agent 选择、预算、重复次数及可比配置。
- 工程窗口：当前步骤、文件变更、终端与测试、产物预览；公开推理折叠保留。
- 观赛视图：保留赛博朋克擂台、VS、动效和解说，把构建成功、回归失败、修复完成等真实事件呈现出来。
- 结果页：最先看到交付结论和证据，可打开补丁、日志和产物，然后进行逐任务比较及重复实验分析。竞技奖杯保留在观赛结算中。

## 6. 实施次序与完成标准

1. **协议和方法边界**：修正上述比较与统计表述；验证更换裁判/验收器或缺少关键版本信息不会被直接列为严格回归结论，旧记录仍可查看。
2. **一个真实任务闭环**：在隔离环境先接 Codex，完整跑通读代码、修改、测试、提交、干净环境复验、产物下载。再接入 Claude，验证工作区和执行过程互不污染。
3. **工程观看与证据界面**：展示 diff、命令、正式测试结果和产物；刷新、断线、取消与回放保持完整，不把 Agent 自述误认成验收结果。
4. **小型实验包**：人工核对约 6 个任务，涵盖缺陷修复、功能增量和数据处理；重复试验作为稳定性摸底，不把少量演示上升为广泛能力排名。

首个可以演示的里程碑：两个 Agent 从相同仓库出发，各自交付补丁；系统在独立验收中证明哪个完成目标、是否引入回归，并允许打开全部证据。它同时提供工程价值、研究材料和可观赏的比赛过程。
