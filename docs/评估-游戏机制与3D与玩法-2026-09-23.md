# 游戏机制 × 3D 效果 × 玩法逻辑 评估报告

日期：2026-09-23 ｜ 评估范围：QuQuArena3D（Unity 客户端）+ arena（引擎）+ production（资产管线）
约束：**真实投稿暂无法进行**——本报告的优化清单全部按"离线/单机可推进"筛选。

---

## 0. 总评

| 维度 | 评分 | 一句话定性 |
|---|---|---|
| 游戏机制 | ★★☆☆☆ | 后端数值机器极其扎实，但**玩家没有任何一个决定能改变赛果**——是"赛事转播台"，还不是"游戏" |
| 3D 效果 | ★★★☆☆ | "代码建世界 + 手写 shader + 实时光路黑洞"工程力强、验证纪律罕见；但零粒子、三套工艺质感并存，战斗演出张力不足 |
| 玩法逻辑 | ★★★☆☆ | 状态机、断点续赛、权威结算的边界清晰；但数值/文案写死、挂起态靠人工补题、mock 确定性坍缩一切悬念 |

最大的结构性事实：**整个产品目前是一台"测量-比较-记忆"机器的高质量演播壳**。好玩的部分（掌击、升降入场、解说舱）全是给录像服务的镜头语言；而真正产生留存的部分（生涯、成就、段位、盘口）要么没接进 3D 客户端，要么已被删除。

## 1. 游戏机制评估

### 1.1 玩法循环逐环体检

| 环节 | 现状 | 离线成立？ | 乐趣 |
|---|---|---|---|
| 开赛 | 选题库/阵容/裁判/档位 + Glicko 抽签预览（`ArenaDuelController.cs:235-342`） | ✅ | 唯一有决策的时刻，但只是"赛事经理" |
| 观赛 | 事件队列演出：掌击/入场/题卡/答卷/解说追问（`ArenaStage.cs:139-154`） | ✅ | 演出合格；mock 结果可预知 → 无悬念 |
| 结算 | Elo/Glicko/赛季/成就/宿敌一次写入（`career.ts:109-247`） | ✅ | 全 loop 数据最扎实的一环 |
| **再战理由** | 回放 / 续赛 / 战报 | ✅ | **断链**：游戏赛"胜负不入积分"（`game-competition.ts:164`、CHANGELOG 3.34.4），赢了不留存任何资产 |

### 1.2 Stakes 机制盘点（决策空间 × 情绪起伏）

- **Elo/段位**：情绪真实（入场报幕、终局 delta），但决策空间为 0，且**3D 客户端零成就/段位入口**（后端 11 成就只活在 CLI/HTML）。
- **盘口竞猜**：**已删未重建**——v2.2/v2.3 曾有完整押注/赔率/积分账本（overview.md v2.2-v2.3），v3.34.4 随直播演出整体移除；现在 `odds.ts` 算出的赔率是"有产出无消费"的纯装饰，3D 端只显示"预期胜率"文本。
- **成就**：一次性解锁，3-5 场摘完低垂果实，无星级/集齐奖励/赛季限定（`achievements.ts:5-6`）。
- **宿敌**：纯统计（n/ahead），无复仇战、无加成。
- **赛季**：日历函数不是玩法时钟，不打就空转，回顾是手动 CLI。
- **每日一擂 daily**：只是个选罐器，无当日榜/连胜/纪录。
- **bracket/league/加赛**：全自动演出，玩家零参与；且 bracket 平局"**Elo 低者晋级**"（`bracket.ts:53-55`）是逆激励——长期压低 Elo 反而在淘汰赛有确定性优势，与生涯 Elo 的正向 stakes 打架。

**核心判断：所有 stakes 都是旁观者 stakes。开赛后到结算之间，玩家决策为 0。**

### 1.3 悬念的根缺陷：mock 确定性坍缩

- mock 答题 rng 种子 = `hash(contestantId::taskId)`（`mock.ts:119`），mock 裁判 jitter 同样确定 → **同阵容同罐下，bracket/league/加赛/3D 对决赛前可算出全部结果**；repeat 恒 W=1、diff 恒"噪声内"。
- 更糟的连锁：`perturb` 对单字 target 恒等（`mock.ts:79-94`）→ 是非/字母罐 mock 全满分 → `distill` 无偏好对（margin=0）→ `mine` 无矿 → **evolve 闭环在这些罐直接空转收官**。
- 注意：确定性本身被契约测试当特性保护（v3.20 行为锚）——**这是"可复现"与"有悬念"的张力，不是 bug**，但产品上必须二选一或分层。

## 2. 3D 效果评估（代码 + 实拍双证据）

技术底座：Unity 6 / URP 17.3 / 场景近空壳（194 行）+ **代码建世界**；8 个手写 HLSL shader，6 个在跑（黑洞测地线光路积分、程序化银河天空、LED 地屏、手绘角色、仪器屏、法阵光束），2 个（SpectrumTrim 彩虹灯带、ShowBeam 摇头光束）被 v19"科考化"刻意下线且有禁用断言（`ArenaResearchCheck.cs:42`）。

### 2.1 实拍读图结论（booths-v26 facilities-03 / slap-v23 实拍帧）

- **黑洞背景是真招牌**（home-1920.png）：吸积盘 + 引力扭曲在实拍里成立，是全项目最强视觉资产。
- **Q 版角色画风可爱、近景撑得住**（arena-1920.png）：手绘感材质 + 面部贴图修复后细节合格。
- **战斗构图有播音感**（reaction.png）：题幕大屏 + 圆形 LED 赛场 + 双侧答案字幕条，转播语言成型。
- **实拍暴露的问题**：
  1. **色调单薄**——全场灰白 + 深青，战斗态没有红/金张力色，"科考站"风格一致性赢了，戏剧性输了；
  2. **道具是"灰模盒子"**——看台、散热片、巡检车全是 Cube/Cylinder 拼装（`ArenaLightShow.cs:52-110`），与 Meshy 角色、Blender 建筑**三种工艺质感并存**，远景看台像未上材质的 blockout；
  3. **UI 遮挡**——终局"冠军·学霸-o9"地屏字幕被"模型展馆→"按钮压住（reaction.png）；
  4. **近身站位余量薄**——掌击固定近身（slap-v23 移除走近/后退），实拍两角色几乎贴模；
  5. **角色在场馆中占比过小**——俯瞰构图（glass-live-duel.png）大面积空地屏，主角只剩两个小点；
  6. 截图带 **Unity trial 授权水印**（未裁剪，README 明示）。

### 2.2 管线与预算执行（这是项目的强项）

- 预算纪律严格：JadeChampion 22,975/30,000 三角、credits 逐笔 provenance 可查（玉甲 61/65）；Meshy 生成端就 remesh 到 20,000（`meshy_model_presets.py`）；chibi 三档 LOD 6000/2500/800。
- 验证证据链罕见地完整：每版三分辨率实拍 + 录像 + 射线/球探针净空审计（slap 720 组接掌矩阵最大偏差 2.86cm）。
- 隐患：galaxy-v10 两件 **30,000/29,999 顶满上限无余量**；`width_m 1.6` 预算全项目无核验记录（provenance 只记 height）；贴图 Uncompressed + aniso16 + 2K → 4K 下专用显存 **1.3GB**，mip streaming 未开。
- 性能：RTX 5090 短采样 59.99-60 FPS、draw 138-628、三角峰值 79-211 万——但**无低端机/长时测试**（README 自认）。

### 2.3 特效与光照的"干瘪点"

- **全项目零粒子**（无 ParticleSystem、无 VFX Graph）：胜利只有地屏扩散 + LineRenderer 法阵，掌击没有尘/光/震屏。
- 后处理只真开 Bloom(0.14)+ACES+调色；DOF 显式 Off、MotionBlur 0、无 Vignette。
- 全实时无烘焙：展馆 6 点光 + 舱内点光**全部无阴影**，大空间只有 1 盏主方向光出影，暗部靠 `_GalleryFill` 假补光撑。

## 3. 玩法逻辑评估

### 3.1 结构性优点（值得先说清楚）

- **权威边界干净**：血量/伤害只由后端结算（`ArenaProtocol.cs:51`），客户端纯演出；比赛存档每次 emit 原子落盘 + 启动回读 running→waiting，断点续赛成立。
- **状态机有失败态**：waiting/failure（保留答卷待重试）、waiting/tie（补题续赛）、暂停/终止语义清楚（终止不出冠军）。
- **demo/mock 双向守卫**：mock 模型只能打演示场、演示场禁模型裁判（`game-api.ts:214-232`）——防"假赛当真赛"的闸门在。
- **端口 = 全本机**：连接层强制 loopback http（`ArenaConnection.cs:23-28`），与"sites 冻结、无公开 remote"的投稿红线一致。

### 3.2 玩法逻辑缺陷（按疼痛排序）

1. **游戏赛不进生涯/积分/成就**（`game-competition.ts:164`）——3D 客户端里打得再热闹，赛后什么都不留下；这是"玩完即走"的第一因。
2. **挂起态靠人工**：平局加赛 10 题仍平 → waiting/tie 必须人工选新题库；失败 → waiting/failure 人工重试。长赛程挂起率 2%（历史 28%），无人值守会积压。
3. **写死的数值与文案**：伤害 20×(1−score)、100 HP、场间休息 5s、演示题库 `tongjia-pinyin`、DemoIds 四只 mock——全部硬编码，改赛制要改代码。
4. **演示与真赛同视觉**：OfflineLoop 互殴演出与真赛完全一致，仅一行字幕区分（`ArenaGame.cs:334-345`）——投稿红线 R1-5 专门为此设防，说明风险已被认知但只在"投稿规范"层兜底，不在演出层兜底。
5. **边缘态**：`ArenaDuelController.Receive` 在快照无 duel 时 `Snapshot.duels[0]` 直接索引（空数组越界）；端口双口径（连接层 8181 vs 启动脚本 8182）靠参数弥合，双击 exe 且 Backend 缺失直接退离线。
6. **验证夹具绝对路径写死**在程序集里（`ArenaSpectatorCapture.cs:12`、`ArenaSlapCheck.cs:69`）。
7. **解说不跨进程**：后端重启解说即断（"后端已重启，本条解说中断"）。
8. **3D 端走 0.3s HTTP 长轮询**而非 SSE——与 web 端 BattleBus/SSE 基建不对齐（功能无损，但多一套状态同步面）。

## 5. 一个供决策的思考题

现在的资产排序其实是：**数值机器（A）> 演出工程（B+）> 玩法循环（C）**。而"真实投稿暂无法进行"恰好把最依赖外部反馈的路堵上了——这反而是个机会窗口：把 #1（生涯回流）和 #2（玩家下场）做掉之后，产品从"录给别人看"变成"自己想玩"，投稿解锁时它是靠玩法留人，而不是靠一条掌击视频。

值得想的一个问题：**当玩家自己能下场答题，而模型对手的 mock 行为又是确定的——比赛的悬念应该来自哪里？**（提示：确定性对手≠无悬念，它意味着"背板速通"与"破纪录"两种玩法自然浮现，这正是单人游戏的经典结构。）
